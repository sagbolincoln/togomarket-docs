Contexte

Le commerce en ligne au Togo est en pleine croissance mais manque d'une plateforme marketplace locale permettant aux vendeurs togolais de vendre leurs produits en ligne et aux acheteurs de trouver facilement des produits locaux et importes.

Acteurs & Roles

Le systeme definit 4 niveaux d'acces avec une hierarchie de roles.

🛈
Hierarchie des roles : ROLE_ADMIN > ROLE_SELLER > ROLE_BUYER — Un admin herite de tous les droits. Un vendeur peut aussi acheter.
👀
Visiteur
NON CONNECTE

Utilisateur non connecte. Peut consulter les produits, rechercher, voir les details et s'inscrire.

🛒
Acheteur
ROLE_BUYER

Parcourt les produits, ajoute au panier, passe des commandes, suit ses livraisons, gere ses adresses.

🏪
Vendeur
ROLE_SELLER

Gere sa boutique : publie des produits (couleurs, tailles, images), traite les commandes, gere les expeditions et confirmations.

🛡
Administrateur
ROLE_ADMIN

Gestion complete : utilisateurs, commandes, validation vendeurs, statistiques, categories. Peut marquer les commandes comme payees.

Regles metier

Ensemble des regles de gestion de la plateforme.

1
InscriptionGratuite, cree un compte ROLE_BUYER. Email unique. Connexion automatique.
2
Hierarchie des rolesADMIN > SELLER > BUYER. Un vendeur peut aussi acheter.
3
VariantesUn produit peut avoir des couleurs et/ou des tailles. L'acheteur doit selectionner avant d'ajouter au panier.
4
Panier intelligentMeme produit + couleur/taille differente = articles separes.
5
Commande splitSi le panier contient des produits de N vendeurs, N commandes sont creees avec 1 seul paiement Stripe.
6
Stock atomiqueDecremente via SQL atomique apres confirmation du paiement. Verification avant ajout au panier.
7
Code de livraison6 chiffres genere quand statut → "expediee". Visible uniquement par l'acheteur. Le vendeur saisit le code pour confirmer.
8
Statuts commandepending → paid (Stripe/admin) → processing → shipped → delivered
9
pending → paidUniquement par Stripe webhook ou par l'administrateur (paiements hors ligne).
10
SecuriteLe vendeur ne voit que ses commandes. L'acheteur ne voit que les siennes. Le code livraison n'est pas expose dans l'API standard.

Scenarios detailles

Description complete des cas d'utilisation principaux.

Visiteur CU-V04 : S'inscrire ▼
Acteur
Visiteur
Precondition
Aucune
Scenario principal
1. Le visiteur clique sur "Creer un compte"
2. Il remplit : prenom, nom, email, mot de passe
3. Le systeme verifie l'unicite de l'email
4. Le compte est cree avec ROLE_BUYER
5. Le systeme connecte automatiquement l'utilisateur
6. Redirection vers l'accueil
Scenario alternatif
3a. L'email existe deja → message d'erreur
Postcondition
Compte cree, utilisateur connecte
Acheteur CU-A02 : Ajouter au panier ▼
Acteur
Acheteur
Precondition
Connecte, page detail produit
Scenario principal
1. L'acheteur selectionne une couleur (si disponible)
2. Il selectionne une taille (si disponible)
3. Il choisit la quantite
4. Il clique sur "Ajouter"
5. Le systeme verifie le stock
6. L'article est ajoute au panier avec les variantes
Scenario alternatif
1a. Couleur requise mais non selectionnee → alerte
2a. Taille requise mais non selectionnee → alerte
5a. Stock insuffisant → erreur
6a. Meme produit+couleur+taille deja dans le panier → quantites fusionnees
Postcondition
Article dans le panier
Acheteur CU-A06 : Passer commande (multi-vendeurs) ▼
Acteur
Acheteur
Precondition
Panier non vide, au moins une adresse
Scenario principal
1. L'acheteur va au checkout
2. Il selectionne une adresse de livraison
3. Il clique sur "Payer"
4. Le systeme groupe les articles par vendeur
5. 1 commande par vendeur est creee (status: pending)
6. 1 session Stripe est creee avec le total
7. L'acheteur est redirige vers la page Stripe
8. Apres paiement, le webhook met toutes les commandes en "paid"
9. Le stock est decremente, le panier vide
Scenario alternatif
5a. Stock insuffisant pour un produit → erreur avec nom du produit
Postcondition
N commandes creees, panier vide
Vendeur CU-S11 : Confirmer la livraison avec code ▼
Acteur
Vendeur
Precondition
Commande en statut "shipped"
Scenario principal
1. Le vendeur clique sur "Confirmer livraison"
2. Un modal s'ouvre avec un champ de saisie 6 chiffres
3. Le vendeur demande le code au client
4. Il saisit le code et clique "Confirmer"
5. Le systeme verifie le code cote serveur
6. Si correct : commande → "delivered", code efface
Scenario alternatif
5a. Code incorrect → erreur "Code de livraison incorrect"
4a. Code incomplet (< 6 chiffres) → bouton desactive
Postcondition
Commande livree, code supprime
Admin CU-AD05 : Marquer commande payee ▼
Acteur
Administrateur
Precondition
Connecte admin, commande en statut "pending"
Scenario principal
1. L'admin voit une commande en attente de paiement
2. Il clique sur "Marquer payee"
3. Confirmation demandee
4. Le statut passe a "paid"
Cas d'usage
Paiement en especes, virement bancaire, mobile money — le paiement est confirme hors Stripe
Postcondition
Commande payee, vendeur peut commencer la preparation
